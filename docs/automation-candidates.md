# Automation Candidates

A running list of mechanics and workflows that showed up while building this app and felt reusable — candidates for turning into actual Claude Code skills, agents, or plugins once there's enough real usage across a few projects to justify formalizing them. Nothing here is committed to being built; the point is to not lose a pattern while it's fresh, so it doesn't have to be re-noticed from scratch on the third or fourth app.

Add to this as new sessions surface more. When something on this list actually gets built into a skill/agent/plugin, note that here (what it became, where it lives) rather than deleting the entry — the "why" is worth keeping even after the "what" ships.

## Candidate skills

**Stakeholder interview mode.** `CLAUDE.md`'s Interview Mode (trigger phrase → switch language/tone entirely → cover fixed topics one question at a time → close with a structured bilingual summary appended to a docs file) was hand-written per-project. The mechanic itself — non-technical-stakeholder interview with a fixed topic checklist, conversational pacing, and a structured handoff summary — isn't specific to this app. Worth extracting into a real skill once a second project needs the same shape of interview, parameterized by topic list and target language(s).

**Design-doc scaffold for a new project.** This project's `docs/` set (project-brief, requirements-open-questions, technical-spec, build-log) is a reusable starting structure: health-context/constraints doc, open-questions tracker, implementation spec, chronological decision journal. A "new project docs scaffold" skill could stamp out that same four-doc shape for any new app, prompting for the equivalent of "health context" (i.e., the domain constraints that shape everything downstream).

**Pre-distribution checklist for a mobile/installable build.** The reminder-feature scoping conversation surfaced a cluster of one-time, hard-to-reverse decisions that need to be made deliberately before the first shippable build: signing identity (generate once, back up, reuse forever), package/bundle ID (reverse-domain, chosen for the long term), app display name (checked against unintended scope/liability implications), icon/branding assets. A checklist skill that walks through exactly these before a first Capacitor/native build would have compressed several conversation turns into one pass.

**Schema-migration-free column addition.** Repeated pattern in this project: adding a field to a Sheets-backed type by appending a new column, defaulting a blank cell to a safe value, updating the pure row-mapper functions and their tests, and never touching existing columns. Applied at least three times (`Favorite`, `GlycemicFlag` ×2). Worth a skill that, given "add field X to type Y backed by a spreadsheet tab," does the mechanical parts (interface field, mapper functions, range constants, append-column write helper, matching test fixtures) so the actual conversation is only about the field's meaning and default.

## Candidate agents

**Design-scoping reviewer.** Before implementing a non-trivial feature, this project consistently ran a structured pass that: named the concrete open technical decisions (not just re-described the feature), surfaced rejected alternatives with the reasoning for rejecting them, separated "big" decisions (worth a real back-and-forth) from "small" ones (worth a default + a one-line confirmation), and didn't stop until implementation would need zero further judgment calls. This is close to a repeatable subagent role — "take a feature request and this project's existing architecture/constraints, and return an implementation-ready design with alternatives considered" — distinct from a general planning agent in that it's explicitly optimized to *end* in something buildable without another round-trip.

**Manual-verification-gap tracker.** Twice in this project, full end-to-end verification was blocked by something outside automation's reach (Google's OAuth popup can't be completed by browser automation). Both times the response was the same shape: do everything that *is* automatable (unit tests, build, static review), then write an explicit, concrete manual-check list rather than silently skipping verification or overclaiming it. An agent role that recognizes "this class of thing can't be verified by tooling" and reliably produces the fallback checklist (instead of that judgment call being re-made ad hoc each time) would keep this honest by default.

## Operating principles worth codifying

These aren't skills/agents by themselves, but decision rules that came up repeatedly and could be baked into whatever plugin eventually wraps the above:

- **Fold in vs. ask, by reversibility and provenance.** A small change gets made immediately and just mentioned (not asked about first) when it's low-risk, reversible, and a direct, unambiguous consequence of a decision already confirmed in the conversation (e.g., renaming the app in code once the new name was picked). It gets asked about first when it's creative/subjective (naming options), touches something expensive to reverse (signing, package ID, schema), or isn't clearly implied by anything already agreed.
- **Log decisions where future sessions will actually look.** Every significant design/product decision (not just code changes) got written into `docs/build-log.md` with the reasoning and the rejected alternatives, specifically so a *different* future session could implement or revisit it without re-deriving context. The discipline is less "keep a changelog" and more "write for a reader who wasn't in this conversation."
- **A feature isn't scoped until it needs zero further decisions to build.** Several features in this project were deliberately scoped in one session and built in a completely separate one, with the explicit test being: could that second session implement this without asking anything? If not, the scoping conversation wasn't done yet.
